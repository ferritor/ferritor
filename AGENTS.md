## Crates

Cargo workspace (edition 2024), licensed MIT OR Apache-2.0 (`LICENSE-MIT`, `LICENSE-APACHE`; `license` and `publish = false` in `[workspace.package]`, which every crate inherits with `license.workspace = true` and `publish.workspace = true`, a new one too). A `Cargo.lock` change regenerates `THIRD-PARTY-LICENSES.txt` (the notices the images carry; CI's `lint` fails while it's stale), and a dependency under a license `deny.toml` doesn't allow fails `cargo deny`: a new license goes into `deny.toml` and `about.toml` together (`docs/src/content/docs/contributing/development.md`, "Licenses"). The gRPC contract is `proto/ferritor/v1/ferritor.proto` (`SystemService`: seal lifecycle and key management; `SecretsService`: secrets), compiled by `ferritor-core/build.rs` with `tonic-prost-build`, which needs `protoc` on PATH. If a system tool is missing, ask the user to install it rather than working around it.

- `ferritor-core`: gRPC bindings (`proto::v1`), `crypto` (`RootKey`/`Kek`/`Dek`, AES-256-GCM with purpose-labelled AAD, Shamir via `vsss-rs`, `ShareParams`), `path::SecretPath` and `path::Namespace`, `labels` (label keys, values and limits, checked by the server and the CLI alike), `audit_chain` (shared by the server's writer and the CLI's verifier, so both use one format), `messages` (error reasons and fixed message texts).
- `ferritor-keystore`: the **keys** database (seal config, namespaces, KEK keyring, the workload-identity issuing keys): its migrations and every query against it.
- `ferritor-datastore`: the **data** database, one relation per thing: `namespaces` (each one's KEK floor and version floor), `paths` (every path written: version counter, current version, times, labels, `changed_xid` for the change feed; deleted only with its namespace) and `secret_versions` (ciphertexts and wrapped DEKs, keyed `(path_id, version)`): its migrations and every query against it. The ids (UUIDv7) never leave the crate; the APIs speak paths and namespace names.
- `ferritor-server`: library + thin binary (`main` only wires things up). Modules: `seal` (state machine, holds the unsealed `Keyring`), `root_ledger` (the data database's side of the root key: commitments, floor, the auto-unseal hold's half), `auto_unseal` (the `AutoUnseal` provider trait, `MemoryKms` for tests, the `keep_unsealed` loop) and `aws_kms` (the AWS provider, feature `aws-kms`, on by default), `keyring` (refresh, the KEK check after unseal, the rotate/init/namespace guards), `namespaces` (create, delete, list, labels: both databases), `policies` (stored policies over both APIs) and `policy_store` (verifying them), `rewrap`, `destroy`, `purge`, `ratelimit` (the limiter: GCRA rate, calls in flight, the denial budget, an injected clock; the configured `Limits`, the request scope, refusal episodes; the wiring is in `audit::Gate`), `secrets`, `identity` (workload identity, user docs `docs/src/content/docs/guides/workload-identity.md`: `jwk` and `token` verify a platform's JWTs on `ring`, the algorithm always the key's; `mapping` turns claims into an identity under the issuer's own prefix; `ca` generates the issuing CA and builds the certificates it signs; `exchange` the token exchange with each issuer's keys, served by `grpc::identity_service` on its own listener; `trust` what the TLS layer trusts of what it issued), `grpc`, `http` (JSON API), `tls`, `crl`, `authz`, `policy`, `audit`, `health`, `metrics`, `config`, `watch` (the change feed and its hub; the streams themselves are `grpc`'s).
- `ferritor-client`: library: talking to a server over gRPC, for every client ferritor ships (the CLI, the agent): `connect` (the channel, TLS, the health-call preflight), `retry` (short rate limits waited out), `exchange` (a platform token for a certificate, the key generated and kept in memory), `ServerError` with the reason. It writes nothing to stdout or stderr: what a client tells its user is the client's.
- `ferritor-cli`: library + the `ferritor` CLI, over gRPC only, through `ferritor-client`.
- `ferritor-agent`: library + the `ferritor-agent` binary (user docs: `docs/src/content/docs/guides/agent.md`): keeps an application's secrets current as files. `config` (checked whole at load), `files` (the output directory: generations swapped through `..data`, the previous one kept until the next swap, tmpfs required unless `allow_disk`), `agent` (one round, `Agent::poll(now)`: every decision against the `now` it's given; transient and authoritative refusals), `connection` (rebuilt when the certificate files change, or with workload identity exchanged again when due or after a failed round), `notify`, `run` (`once`, `run`); and `csi`, the `ferritor-csi-provider` binary's (user docs: `docs/src/content/docs/guides/csi.md`): `proto` (the Secrets Store CSI Driver's provider API, vendored in `proto/`), `config`, `request` (a `MountRequest`'s attributes, checked), `provider` (`Mount`, against the `now` it's given).
- `ferritor-testkit`: dev-only: `TestDatabase`, `pki::Ca`, `jwt::TokenIssuer`, `Captured`.

## Invariants

### Keys and databases

- The two databases stay separate, and each is touched only by its own store crate. `secrets.kek_version` points across them, so the server enforces it, not a foreign key.
- The root key is never persisted. A KEK is never destroyed except through `destroy` (the KEK floor, below); retiring is bookkeeping only and retired KEKs stay stored and loaded, because a stale server may still write with them.
- A path's first segment is its namespace (`SecretPath::namespace`); there's no default namespace, and nothing can be stored outside one. Each namespace has its own KEK lineage: a KEK is (namespace, version) everywhere (keys table, keyring, floor, reports), and its wrapped key's AAD binds both (`RootKey::wrap_kek`), so a KEK row moved to another namespace doesn't open. A deleted namespace keeps its row and its destroyed KEK rows, so a re-created one continues the numbering and its first KEK lands exactly on the floor the delete raised.
- AAD binds path + version, so paths must be canonical: everything goes through `SecretPath`, which rejects (never normalizes), and the crypto API only accepts `&SecretPath`. The `paths.path` CHECK mirrors the rule. A path's text and a namespace's name are immutable (a trigger refuses any update, `FR003`: renamed, every version under it would stop decrypting), a path's `namespace_id` is the namespace its text names (the composite foreign key `(namespace_id, namespace) → namespaces (id, name)` on the generated column `paths.namespace`, the path's first segment), and a version's `namespace_id` is its path's (the composite foreign key `(path_id, namespace_id) → paths`), so the per-namespace KEK queries and the floor see every row where it belongs: a mismatch can't be stored, with no trigger to maintain.
- Version numbers are never reused: `begin_put` takes the next one under the path's lock as one past the higher of `paths.highest` and the rows' own highest (a row written without bumping `highest`, by a hand repair or a restored backup, must not collide), never from the rows alone, which purging removes, and never below its namespace's `version_floor`. `paths` rows are deleted only by a namespace's deletion (`Datastore::reclaim_paths`: no version at all under it, checked under its KEK floor lock taken exclusively, after the floor is past its every KEK), which first raises the namespace's `version_floor` to the highest any of them reached, in the same transaction, so a re-created namespace's paths number on past it (`deleting_a_namespace_reclaims_its_paths_and_never_reuses_a_version`). It deletes with `FOR UPDATE SKIP LOCKED`, never waiting for a row: a put in flight holds its `paths` row and waits for the floor lock at its insert, so waiting would deadlock (`a_put_in_flight_never_deadlocks_its_namespaces_reclaim`); the row stays, and the floor refuses that put. KEK versions too: a destroyed KEK keeps its row.
- `paths.current_version` is the path's latest live version (NULL with none), what listings read through `paths_live`: every write that can change it sets it in its own transaction, under the path's lock: a put (its own version, in the `paths` upsert), a delete (NULL), a restore (the higher of it and the restored one). Trims never delete the latest version and purge only deleted ones, so they leave it alone; a new write that changes which version is live must set it too. A test fails if it drifts: `the_store_matches_a_model_through_any_writes` (a proptest of random puts, trims, deletes, restores and purges against a model) and the end of the store's purge, restore, rewrap and trim tests (`assert_current_versions_agree`). Listings also check the version they find is live, so a wrong `current_version` would hide a path, never show a deleted version.
- A namespace's first write creates its `namespaces` row in a statement of its own, committed at once, after ending the put's transaction (then the put starts over): inside the put, a concurrent first put to another path of it would wait for this one's commit.
- The one way past the namespace-creation guard is `Namespaces::create_past_lost_keks` (`Numbering::PastLost`, the only caller allowed to skip numbers): no live namespace, rows under it, first KEK past every version in use (rows, floor, keys database, this server's held KEKs), floor raised to it first and rows re-checked after. Keep plain create refusing.
- Rotate, init and namespace creation go through the guards in `keyring` (`ensure_keys_not_behind` per namespace, `ensure_no_orphaned_rows`, from the `grpc::System` handlers, which hold their own `Datastore`; `ensure_namespace_free`, from `Namespaces::create`): after a mismatched restore, any of them would reuse KEK versions rows already use, making the mismatch permanent. Cross-database checks belong where both stores are reachable, never in `Seal`.

### Seal, epochs, rekey

- An unseal accepts a root key only if a root commitment for its generation in the data database verifies (`RootKey::root_commitment`: HMAC over the generation under an HKDF subkey, `ferritor.v1.root-commitment`; `root_ledger`, reached through `Seal::with_root_ledger` as the floors are, so `Seal` holds no `Datastore`) and its generation isn't below `root_generation_floor`. The floor is read **before** the keys database (it only rises after a keys-database commit), and the check runs before the keyring loads. Commitments are insert-only (a trigger, `FR004`); init (refused once the floor is above 0, whatever the keys database says) and rekey insert theirs before the keys database commits, and raise the floor after, retried in the background. Only shares re-commit (`unseal --recommit`), when no commitment for the generation verifies, never below the floor, and only once a stored secret version (DEK and ciphertext, one tried per namespace and KEK version) opens under the key: shares prove *a* root key, not the one the data was written under (`a_substituted_root_key_is_refused_and_cant_be_recommitted`).
- Auto-unseal (`[seal] provider = "awskms"`) is a second way to open the same root key, never a replacement: the shares stay shares of it (the recovery shares) and unseal in every mode. The KMS key comes from the config, never the keys database; every `Decrypt` names it. An auto-unseal reads the root-generation floor before the keys database, `seal_config` and the wrap in one snapshot (a wrap of another generation is `WrapMismatch`, never unwrapped), and accepts the unwrapped key only after `root_check` and the root commitment, as a shares unseal; KMS never re-commits. Init with a provider wraps first (a refused `Encrypt` stores nothing), a rekey wraps its new key once the new shares are verified and before the commitment and the keys database's transaction (never under `seal_config FOR UPDATE`), and its commit stores that wrap and deletes every other (a server configured for Shamir alone leaves none). So `rekey_start` compares this server's provider and key with the stored wraps at the current generation and refuses a mismatch (`RekeyWouldChangeSeal`) unless asked to change them (`rekey_start_changing`, `--seal shamir|awskms`, recorded in the audit entry): config drift on one server must never change every server's mode or key unasked. An attempt makes its KMS calls and the reads before them without the admin lock (`status` and submitted shares never wait behind KMS), then under it re-checks it's still sealed and the generation unwrapped is still the stored one before the commitment check and the publish. The loop (`keep_unsealed`) retries `kms_unavailable` with backoff, looks again every `MAX_WAIT` while held, waiting, `denied`, `root_commitment` or `below_floor` (so a re-commit elsewhere brings it up), and stops only on `mismatch` until the server is unsealed some other way. `wrap` returns the key that actually wrapped (`Wrapped::key_id`), stored with the wrap. A KMS endpoint is https, or http on loopback only (`http::is_loopback_host`, never DNS).
- The auto-unseal hold is a pair of counters (hold, released) in **both** databases (a table `auto_unseal_hold` in each), written only with GREATEST; a server auto-unseals only if each shows `released >= hold`, and a half that can't be read counts as held. `seal_now` also sets this process's own hold (`local_hold`) in the critical section that drops the keyring, so this server's loop, woken by that very seal, can't undo it before (or without) the databases' hold landing; only a publish of an unsealed keyring clears it (`the_loop_never_undoes_its_own_seal`). `ferritor seal` then sets the databases' hold (one past the higher hold read) in both modes and on a sealed server too, **after** dropping the keyring, reports `hold_set` honestly and retries a failed half in the background (`ferritor.seal.hold_pending`), never waiting on it. Only an explicit release releases it (`unseal --auto`, `--release-hold`, both the `unseal` permission alone), setting `released` to the higher hold it read; a plain shares unseal doesn't. The keys database's half is a table of its own (`auto_unseal_hold`), never `seal_config`, so a seal's write doesn't queue behind its row locks. An attempt reads the hold before calling KMS and again right before publishing (`a_seal_during_an_attempt_wins`); a held server's loop makes no KMS call. The key's ARN and KMS error text appear in a status only for callers who may `unseal` (`grpc::seal_status`).
- Seal is the emergency stop: once permitted it never returns an error. It drops the keyring first (`seal_now`), before taking the admin lock, so nothing can delay it; add no work before that. Every seal bumps an epoch, and `publish` refuses a keyring from any call that began before the latest seal (admin calls read `epoch()` before waiting for the lock). Keep the admin lock held until a pending rekey's outcome is known, so no unseal with the old shares can race an unfinished commit.
- Once seal returns, no request may use the keys. Secret operations record `Seal::unsealed_epoch` when they start and take the keyring only right before their crypto via `keyring_at(epoch)`, never holding it across an await. Writes re-check with `ensure_unsealed_since` right before committing; list re-checks before answering.
- `Seal::sealed_changes` (the watch the health service follows) is set only where the keyring is dropped or published, under the same lock.
- Rekey: never commit a new root key before a threshold of its new shares is verified. A failed commit call doesn't prove nothing was stored: never discard a pending root key on error without `Seal::is_committed`, whose re-read must be `Keystore::settled_seal_config` (`FOR SHARE` with a `lock_timeout`), not the plain `seal_config`, which can see the old row just before a commit lands; a timeout means unknown, and the key is kept. Nothing may fail after a commit succeeds. The commit re-wraps from the keyring at commit time (so a rotation in between is covered), and skips destroyed KEKs.
- Rotate and rekey lock `seal_config` (`FOR SHARE` / `FOR UPDATE`) so they serialize; `Keystore::destroy`, `create_namespace` and `delete_namespace` take `FOR SHARE` like a rotation (a rekey commit must re-wrap exactly the stored KEKs).
- Every reply carrying a status shows a rekey nonce only to callers who may `Rekey`, built in one place (`grpc::seal_status`).
- The workload-identity issuing key lives like a KEK: wrapped by the root key (`RootKey::wrap_issuing_key`, purpose `ferritor.v1.issuing-key`, bound to its version), unwrapped into the `Keyring` (`IssuingKeys`), so a seal drops it with everything else; loaded at unseal and by the refresh snapshot; created and rotated under the admin lock with the seal config `FOR SHARE` (`Keystore::create_issuing_key`, `rotate_issuing_key`), and re-wrapped by a rekey commit, which re-reads the active key under its lock, as it does the policy key (and `rekey_start` refuses early while it won't open, `IssuingKeyUnusable`). Only the active key's private part is ever stored: a rotation erases the old one's and keeps its certificate (the schema's `issuing_keys_active` CHECK). An active key that doesn't load is logged and left out, never an unseal's failure: nothing but issuing depends on it. A certificate it issues is built by ferritor alone (`ca::IssuingCa::issue`): from a CSR only its public key, after its signature verifies, never a name, an extension or a validity it asks for.
- The issuing keys are one set (`IssuingSet`): every row's version, certificate, state and `retired_at` (`StoredIssuingKey::record`), MACed with the set's revision under the root key (`issuing_set.tag`, `RootKey::tag_issuing_set`, purpose `ferritor.v1.issuing-set`). Trusted only if the MAC verifies at a revision not below the floor: the higher of the data database's `issuing_revision_floor` (read through `RevisionFloor` with `Floor::IssuingKeys`, **before** the keys database, as for the policies) and the highest this process saw (`Seal::issuing_seen`, kept across seal and unseal). A set that isn't is trusted not at all (`IssuingKeys::load` → `IssuingUnverified`): a refresh keeps the keys in force, an unseal has none, and the failure is logged when it starts or changes. Every write (create, rotate) runs under `lock_issuing_set` and the seal config `FOR SHARE`, re-tags the whole set as it now is at one past the higher of the stored (verified) revision and the known floor, and raises the floor after its commit; any server verifying a set above the floor as it knows it raises it (`Seal::issuing_verified`), so a missed raise is caught up. A rotation retires (trusts on) the old key only if its stored certificate is the one this server loaded with its key, else revokes it; `--now` revokes every retired key too; on a set that doesn't verify (or is below the floor) only a revoking rotation is allowed (`IssuingKeysUnverified` otherwise), and it revokes every key in it and takes its revision from the floor, never from the unverified set. A rekey commit re-tags the set under the new root key only if the current one verifies it (`RekeyRewrap::issuing_tag`), so a forged set is never laundered. `retired_at` is written in whole seconds (the MAC covers seconds). Each CA's name has a random part (`ca::generate`): certificates are routed by issuer name, so no two CAs may share one, a version number reused after a restore included.
- The SIGHUP keyring refresh runs in its own task (`main`'s `reload_on_hangup`): the policy reload, how access is revoked in a hurry, must never wait behind the admin lock or the keys database.
- `Seal::refresh` reads the KEKs, their states, the namespaces and the seal config from one snapshot (`Keystore::snapshot`, a REPEATABLE READ transaction), so they always agree: a rekey (`RekeyedElsewhere`) or a namespace deleted and created again lands before all of them or after. Don't split it into separate reads.
- `Seal::refresh` handles each namespace in one of three ways: present in the keys database (load its KEKs; drop only the destroyed ones), marked deleted (drop it with its KEKs: its floor fences them off), or absent altogether (a lost creation: keep all its KEKs as vanished, with no active one). So a refresh never drops a KEK the keys database didn't destroy: one that's gone from it (a lost rotation or namespace) is kept in the `Keyring` as **vanished**, for reading only, since this server's copy is the last. The active KEK is always a stored one, so a vanished KEK never wraps a new DEK; rewrap unwraps with it, which is the rescue. A rekey commit re-wraps only stored KEKs (the keys database must cover exactly its own versions); rotate and destroy carry the vanished set forward, dropping a version the keys database has again. Rewrap's last step releases each vanished KEK no row uses any more (`Seal::forget_vanished`), so a rotation reusing its number never meets two keys under one number.

### KEK floor (destroying KEKs)

- The data database's `secret_versions_kek_floor` trigger refuses any insert or `kek_version` update below the floor (`FR001`). There's one floor per namespace, `namespaces.kek_floor` (1 until raised, and for a namespace the data database has no row for; a raise upserts the row; the trigger finds it by the row's `namespace_id`, reading the name before the lock, which is safe because names are immutable, and the floor after it). Writers take the namespace's floor lock (advisory, class 2, object `hashtext(namespace)`) shared, a raise (`Datastore::raise_kek_floor`) exclusive, so the raise waits for that namespace's writes in flight and its writes after it see the new floor. The floor is only raised, never above the active version (two exceptions, both while the namespace has no active KEK to write with: deleting it raises the floor to one past its highest, and a recovery past lost KEKs raises it to the KEK it is about to create).
- The trigger reads the floor after taking the lock, which is only sound in READ COMMITTED (a volatile function's statement sees what committed before it began; a REPEATABLE READ snapshot could predate a raise), so it refuses writes in any other isolation level (`FR002`). Data-database writes must stay READ COMMITTED (the per-path lock relies on it too).
- `Destroy::run`: retired, raise the floor past v, then check no row uses v, then erase in the keys database, then drop it from the keyring. `Namespaces::delete` is the same for a whole namespace: empty (no row, deleted ones included), raise its floor past its highest version, check empty again and reclaim its `paths` rows (one transaction), then destroy its KEKs and mark it deleted. That order is the guarantee; don't reorder or skip a step.
- A put refused by the floor refreshes (sharing the reads' on-demand cooldown, `Secrets::refresh_on_demand`) and retries once, only with a newer active KEK.
- Rewrap moves rows compare-and-set (`Datastore::rewrap`: only rows still on the old version), takes the keyring per batch with `keyring_at(epoch)` (never across an await), and retires a version only when no row at all uses it: rows that failed to unwrap count as using their KEK, so it's never retired, nor destroyed.

### Writes and locks

- Writes to one path (put, delete, restore) take the path's transaction-scoped advisory lock (`Datastore::lock_path`, class 1); deletes and restores must take it too, or one could commit between a check-and-set's check and its put. Between taking it and `PendingPut::insert` only synchronous crypto: no awaits under the lock beyond the write itself. Check-and-set compares `PendingPut::latest`, read under the lock.
- Trimming (`max_versions`) happens in the put's own transaction, under the path's lock (`PendingPut::insert`): one index range, never a scan, and never the latest version, which is why check-and-set is unaffected.
- Purge deletes with `FOR UPDATE SKIP LOCKED`, so concurrent passes take separate batches and a row a restore (or rewrap) holds is left alone; it never touches a live version and never frees a version number (`paths.highest` stays). In the same transaction it then clears the labels of paths left with no versions, in two statements, never one: first it locks those `paths` rows (`FOR UPDATE`, in id order, so concurrent purges lock alike), which waits for a put or a label change holding one; then a new statement, whose snapshot is taken after the locks, clears the labels where no version exists. One statement would re-check its `WHERE` after waiting for a lock but read its `NOT EXISTS` from the old snapshot, missing a version a put committed meanwhile, and clear that put's labels. A label change locks the `paths` row first, then checks in a statement of its own that a version exists (a subquery of the locking statement would have the same stale snapshot); a put holds its `paths` row from its upsert. So a path with nothing stored has no labels at any commit; metadata and labels treat it as `NOT_FOUND`.
- Lock order between a path's rows: a write that updates both a version row and the `paths` row (delete, restore) updates the version rows first. Purge holds the deleted versions it removes while it waits for their `paths` rows, so a write holding a `paths` row while it waits for one of those versions would deadlock with it. Puts and label changes take the `paths` row first, which is safe only because they never wait for a deleted version (a put's trim touches live ones).
- Every store call goes through `bounded` (client-side timeout: Postgres's own timeouts can't see a hung connection); a timeout is `Timeout`, and for a write its outcome is unknown. Lock waits set a `lock_timeout` (→ `Busy`), always at least 1 ms (0 means no limit). Migrations run on a separate connection without `statement_timeout`.

### Authorization and audit

- Every secret operation asks the authorizer before the seal check, and before the namespace matters: `NO_NAMESPACE` is only ever told to a caller authorized for the path, so it can't be used to enumerate namespaces. `status` shows namespace totals only, never names; names are behind the `namespace` action. Deleting a namespace needs `namespace` and `destroy_kek` (it crypto-shreds every backup of its rows); every `SystemService` handler calls `System::allow` first of all, before reading the epoch or taking the admin lock.
- Two kinds of rules (`docs/src/content/docs/guides/policy.md`): the config rules (`policy::Policy`, `[[policy]]` in `ferritor.toml`) and the stored policies (keys database, `policies`). Stored policies grant **secret actions only**, enforced when written (`ferritor_core::policy::SecretAction`) and when loaded; admin actions, `policy` included, come from the config alone, so the API can never create an admin and the way in never depends on the database. `Gate::decide`: config rules first; only for a secret action they don't allow, the stored policies (`authz::StoredPolicies`, implemented by `Seal`). While those aren't in force (sealed, or the set didn't verify) such a request is **undecided** (`SEALED`, `POLICY_UNVERIFIED`), audited as `sealed`/`unverified`, never a denial; an admin action the config rules don't allow is always a plain denial.
- Stored policies are in force only verified (`policy_store::verify`): every row's HMAC and the set's (over the revision and every row) under the policy key, which is wrapped by the root key (`seal_config.wrapped_policy_key`, purpose `ferritor.v1.policy-key`). Never put into force, nor build a write on, a set that doesn't verify: keep the last verified one (a refresh), or none (an unseal); only `apply` with `prune` replaces an unverified set, and only it (or the very first write: revision 0, with key, set MAC and rows all absent; all absent at a later revision were wiped, `KeyMissing`) may create a policy key. A key missing next to a set, or one that won't open, is an integrity failure, never a fresh start. Key and set come from one snapshot (`Keystore::policy_snapshot`), so a refresh always adopts the stored key. The highest verified revision lives in `Seal` for the life of the process, across seal and unseal, and the highest written one in the data database (`policy_revision_floor`, read through `policy_store::RevisionFloor`, which `main` gives `Seal` with `with_revision_floor`, so `Seal` never holds a `Datastore`): every load and every policy write reads the floor into the remembered revision **before** the keys database's snapshot (the floor only rises after a keys-database commit, so a snapshot read later is never below it), and a write raises it after its commit, and any server whose verified set is above the floor as read at that load (lowered or not: a read replaces what the server knew) raises it to that set's revision (`Seal::catch_up_policy_floor`), so a missed raise (a failure, which doesn't fail the committed write; a failover that lost it) is caught up by the next server to verify the set. A revision below the remembered one is a rollback, a wipe to revision 0 included, so rolling the set back takes write access to both databases; a floor that can't be read is `Unreadable` for a load, and refuses a write. A write's revision is one past the higher of the stored and the remembered one. The whole set is re-verified once a minute on its own schedule (`main`'s `reverify_policies_periodically`), never tied to the keyring refresh or the poll, which may be off. `Gate::stored_policies_reloaded` logs and audits a failure only when it starts, changes or ends (`recovered`); every attempt is counted.
- The verified set is published next to the keyring (`Published::policies`): an unseal verifies it first and publishes both together; `seal_now` drops both in the same critical section (no other work). Policy writes serialize on `policy_state FOR UPDATE` and hold the seal config `FOR SHARE`; a rekey commit re-reads and re-wraps the policy key under its lock (and `rekey_start` refuses early while it won't open).
- `Secrets` and `System` only hold an `audit::Gate`, so asking always records. `Gate::permits` is the one unrecorded question, for three uses only: shaping a reply, the rate limits' exemption (below), and a watch stream's checks before each change and every `RECHECK` (`Secrets::still_watching_where`), which fall back to the recorded check only when it says no, so a refusal is recorded and ends the stream (the stream's opening is recorded, every item).
- Every allowed call that changes state records an outcome (`Gate::outcome`, `"event": "outcome"`) once done: every admin call but `status`, every secret write from either API. A failure at a write's commit is `unknown`, not `failed` (the connection can drop after Postgres commits; `secrets::Failure::at_commit`), as is any write the database didn't confirm in time. A failed call that still changed something says so in its details.
- The audit log fails closed: an allowed request whose entry isn't written and flushed within the timeout is refused before touching any data. Seal is the exception (queued, never waited for); outcomes are queued too, and so are the rate-limit episodes (below). A rate-limited request has no entry of its own: it's refused before the decision, having touched nothing.
- Stdout carries the audit log and nothing else (logs go to stderr). Never log or audit values, shares or nonces; never log the audit signing key. Label changes are audited by key only, never their values (labels aren't secret, but they needn't be in the log). The writer uses a duplicate of fd 1, not `io::stdout()`, which silently swallows writes to a closed stdout.
- Only the writer thread links lines into the chain (the one place lines are ordered). Never call a chain proven unless it ends in a valid `chain_end`: `chain_start` isn't signed. Nothing after a `chain_end` belongs to its chain: damage there is outside any chain (`Report::stray`, unproven), an entry there breaks it.
- At shutdown `Drain::wait` queues the signed `chain_end`; anything written after it starts a new chain. A write that fails ends its chain: the writer ends any partial line with a newline and starts a new chain on the next write (the verifier tolerates a damaged line only as a chain's last).
- Tests read entries through `ferritor_testkit::Captured::lines`, which hides the chain's own lines (`chain_start`, `checkpoint`, `chain_end`) and fields (`seq`, `prev`); `Captured::raw` has the bytes, chain included. A test counting or comparing entries must use `lines`, or the chain's lines throw it off.

### Rate limits

- Admission happens in `Gate::check`, at a request's first check only (`ratelimit::Request::claim`), before the decision, in this order: the denial budget, the identity's in-flight slot, its rate, then a permit under the server-wide cap. The in-flight slot is counted only once the rate passes, and taken before the server-wide wait, so one identity can't queue any number of calls on the cap. The admission (`Slot` and permit) lives in the request's scope until the request ends.
- Nothing is limited outside a request scope (`ratelimit::in_request`, opened by `tls::Detach` for every route, both modes): background work (purge, rewrap passes, refreshes) and code driving `Secrets` directly never are. Every call counted in `ferritor.in_flight` goes through the same scope.
- Admin actions the config rules allow are exempt (`Gate::permits`, unrecorded), so an operator's seal is never throttled; never exempt anything a stored policy grants, or an admin action by a non-operator.
- The server-wide wait is cancellable until the permit, never after: it `select!`s on the request's `CancellationToken` (cancelled by Detach's drop guard when the client leaves), so a call nobody waits for never starts; once the permit is held, the call runs to its end like any other (Detach). Over the wait (`database_timeout_ms`) it's `UNAVAILABLE` (`Refused::Overloaded`).
- The denial budget is charged only after a recorded `Denied`, never for an undecided request (`sealed`, `unverified`: the server's state, not the client's doing), nor for a refusal by a limit.
- Refusals are audited as episodes (`ratelimit::Episodes`: one entry when a key starts being refused by a limit, one with the count once it's been quiet for `QUIET`), queued like outcomes; never per request, never ended at the first request let through. A certificate naming no caller is limited by fingerprint in `Gate::rejected`; over it, its rejection isn't audited.
- `server_max_in_flight` is read at startup only (a `OnceLock`d semaphore); everything else reloads on SIGHUP into the same `Limiter`, so counters and buckets carry over (a reload never refills a burst). Limits are per server.
- Answers: `RESOURCE_EXHAUSTED` with reason `RATE_LIMITED`, the limit in `ErrorInfo` metadata `limit` and a `RetryInfo` (`grpc::rate_limited`, the one place); HTTP 429 with `Retry-After` from it. The clients' retry (`ferritor-client`'s `retry`) is safe for every call only because a limited request is refused before anything runs: keep admission before any work.

### Transport and HTTP

- Per-request checks in `tls::identity`: every presented certificate valid now, and the client certificate not revoked: by the CRLs, or, for a certificate an issuing CA signed (`tls::WorkloadTrust`, implemented by `identity::trust::Trust`, matched by issuer name), its CA still trusted (active, retired within `MAX_LIFETIME` of its retirement, never revoked; none while sealed, the CAs last seen then untrusted), its identity under an issuer still configured, issued after any cutoff, and no longer-lived than `MAX_LIFETIME` (plus the backdating). At the handshake `ClientAuth::route` sends a certificate by its issuer's name to a verifier of the trusted issuing CAs (no CRLs) or to the client CA's; never add an issuing CA to `client_ca`'s roots, whose verifier would need a CRL for it. A handshake alone isn't enough (long-lived HTTP/2, resumed TLS sessions keep the original chain). `tls::serve` puts the CRLs in each request's extensions (`tls::Revocation`); a certificate without it is refused. The handshake verifier (`tls::ClientAuth`) and the per-request CRLs are swapped together.
- CRL load checks mirror what rustls checks at the handshake (plus RFC 5280's cRLSign rule), so a bad file fails at load, not at every handshake.
- Every request runs in a task of its own (`tls::Detach`, applied by `tls::serve` to every route, both modes), so a client that disconnects or times out can't cut a call short: hyper and h2 drop the request's future with its connection, and a write dropped after its `COMMIT` was stored with no outcome. Don't serve routes around it, and don't rely on a client's presence to finish a call. The drain waits for these tasks after the connections.
- The JSON API: no CORS headers, no state-changing `GET`, no endpoint accepting form or text bodies (`PUT`/`PATCH`/`DELETE`, `POST` only with a JSON body even when empty), so every state change needs a preflight the server never grants. Plaintext serving answers only requests addressed to loopback (`http::loopback_hosts_only`, applied by `tls::serve` to every route).
- Both APIs call the same `Secrets` (and `Policies`: the policy endpoints are the JSON API's one admin surface; every other admin operation is gRPC only), and HTTP errors go through the gRPC `Status` mapping, so both answer alike. Transport limits are computed from `secrets::MAX_VALUE_SIZE` and `labels::MAX_LABELS_SIZE` (`grpc::MAX_MESSAGE`, `http`'s `BODY_LIMIT`, the latter for JSON's worst escaping), so the largest put fits through both APIs; a test sends it through each. The policy endpoints' limits come from `ferritor_core::policy::MAX_APPLY_BYTES` (`grpc::MAX_POLICY_MESSAGE`, `http`'s `POLICY_BODY_LIMIT`), so the whole stored set fits in one apply, the repair.
- Internal errors are logged, never sent. Where the gRPC code alone is ambiguous, attach a reason from `messages::reason` (`grpc::with_reason`); programs and the CLI's hints match the reason, never the message. A new ambiguous condition gets a new reason (and a row in `docs/src/content/docs/concepts/architecture.md`).
- Metrics attributes are small fixed sets: never paths, identities, certificate fingerprints, namespace names or values. `metrics::init` runs before anything records.

- The token exchange (`IdentityService`) is served only on `[identity] listen_addr`, with `ServerTls::without_client_auth` (same certificate resolver); the main listener always requires a client certificate. It records each issuance with `Gate::exchanged` and waits for the write before returning the certificate (fail-closed, `UNAUDITED`); refusals are queued, per peer IP under `ratelimit::UNAUTHENTICATED` and episodes past it (`Limit::ExchangeRefused`). Exchanges are limited per identity they map to, after the mapping and before any signing or audit wait (`Gate::exchange_admitted`, `ratelimit::exchanges` with the issuer's `exchange_burst`, `Limit::Exchanges`; the clients honour its `RetryInfo`: the agent through `ConnectionError::retry_after`, the CLI through `retry`): the listener has no caller, so no other rate limit applies there. An unknown `kid` refetches only the token's own issuer's keys (`TokenError::UnknownKey { issuer }`), at most every `MIN_REFETCH`. A template's every claim is a whole path segment (`mapping::Template::parse` refuses `{a}-{b}`, `x-{a}`): claim values may hold `-`, `.` and `_`, so two in one segment can give two workloads one identity. Never audit or log the token. An issuer's keys are only that issuer's (selected by `iss`, then `kid` among them), the algorithm comes from the key, and no config rule may name an identity under an issuer's prefix (`config`).

### Watch streams

- The change feed (`watch::Watch::run`, one per server) reads `paths.changed_xid`, set by the `paths_mark_change` trigger whenever `current_version` changes: every write that moves the live version sets `current_version` (above), so the feed sees it with no code of its own in the writes. Never `NOTIFY` from a write: it serializes committing transactions (a put went from 5,366/s to 1,099/s, `docs/src/content/docs/operations/performance.md`).
- `Datastore::changes_since` reads its new snapshot and the rows in one REPEATABLE READ, READ ONLY transaction (the one data-database transaction not READ COMMITTED, allowed because it writes nothing), so a change is in exactly one answer, a late commit included. A mark is good only on the Postgres server that took it (`pg_postmaster_start_time`): otherwise `Restarted`, a `Resync` for every stream, since a restarted or promoted server may give transaction ids again. A failed poll retries from the same mark. A subscription is taken before waiting for the feed to be live, and `ready` sent only after, so no change after `ready` is missed. A stream that falls behind (`Lagged`), or more changes at once than `MAX_PER_POLL`, is a `Resync`, never a silent drop.
- `WatchSecrets` is a request like any other at its open (admission, then a recorded `Read` per path and `List` `Below` per prefix, before the seal check). The stream itself runs in a task of its own outside the request scope: not counted in flight, its checks not rate limited. Before each change it sends, `Secrets::still_watching_change` asks again (`Gate::permits`, unrecorded; only for one no longer permitted the recorded check, whose refusal ends the stream); every `RECHECK` the certificate as `tls::identity` checks it (expiry, CRLs, workload trust) and every permission. It ends at a seal (`Seal::sealed_changes`), at the certificate's `notAfter`, and at `Watch::close`, which `main` calls when the drain starts (a stream lasts as long as its client, and would hold the drain to its limit). A change carries a path and a version, never a value or a label. Streams are capped per identity (`Quota::max_watch_streams`, `[rate_limit] max_watch_streams`, default `watch::DEFAULT_MAX_PER_IDENTITY`), counted by the `Subscription` like its server-wide permit, so no identity holds every one of `MAX_STREAMS`; both refusals are `WATCH_FULL`, with `limit` `identity` or `server`.
- A stream is an optimization for its clients, never their only way to learn: the agent's rounds and the provider's shared window stay in force without one.
- The feed follows the oldest transaction running at each mark (`ChangeMark::oldest_running`, `Watch::note_held`): one held open holds every poll's lower bound back (transaction ids are the Postgres server's, every database's), so it's warned of once past `HELD_BACK_WARNING` and shown by `ferritor.watch.feed.held_back`.

### Images

- The `Dockerfile` builds every binary once, statically against musl, and each image is one binary in `scratch`: nothing else unless its stage copies it (the server's: the CA bundle, for the AWS KMS client). A binary that comes to need a file at runtime (a CA bundle, timezone data, a helper program) gets it copied into its stage, or it fails only in the image; `e2e/cluster.sh` runs the server and the provider from their images, and CI builds the other two.
- The server's musl build allocates with mimalloc (`#[global_allocator]` in `main`, `cfg(target_env = "musl")`): musl's allocator made reads 2.8 times slower (`docs/src/content/docs/operations/performance.md`, "The images"). Keep it, or measure again.
- Each release publishes the four images to ghcr.io (`release-plz.yml`'s `images` and `image-tags`: `ghcr.io/ferritor/ferritor-<target>`, amd64 and arm64, the version and `latest`), from the commit `release` tagged, never from a later one, and signs each by digest with cosign, keyless (`image-tags`, `id-token: write` there only). The identity users verify is `release-plz.yml` on `main` (`docs/src/content/docs/getting-started/kubernetes.md`): renaming the workflow, moving the signing to another one or running it from another ref changes it, so the docs' `cosign verify` command changes with it. A new target is added to both jobs' loops.
- The build context is an allowlist (`.dockerignore`): a new directory the build needs is added there; `.env`, `target/` and keys never are.

### Startup and shutdown

- `main` calls `ferritor_server::forbid_memory_access` (`PR_SET_DUMPABLE` 0) first of all, before `.env` or anything secret is read, and refuses to start if it fails: no core dumps, no same-user ptrace or `/proc/<pid>/mem` (`tests/hardening.rs`). Keep it first. Then the arguments: none but `--version` and `--help`, any other refused (`tests/arguments.rs`); the server's configuration comes from `ferritor.toml` and the environment only.
- `main` loads `.env` only in debug builds (`cfg!(debug_assertions)`): dotenvy searches every parent directory, so a release build could pick up another application's `.env` and its `FERRITOR_*` lines.
- Catching SIGINT/SIGTERM replaces the default exit, so `main`'s `watch_signals` must provide every way out: during startup exit at once; serving, the first signal starts the drain (readiness off, then the optional delay, then draining, bounded by `DRAIN_LIMIT`), a second exits at once after a short audit flush. tonic 0.14.6 panics with `max_connection_age` but no grace, so the grace is mandatory.

### Client

- Shares and secret values are never command-line arguments: stdin, with a hidden prompt on a terminal. Results to stdout, guidance and warnings to stderr.
- An exchanged certificate's key is generated by the client and never written anywhere but `ferritor login --key-out` (mode 0600, created fresh); tokens are read from a file, never a command-line argument.
- Over https `ferritor_client::connect` makes a health call first, so "nothing was sent" is certain before a real call (`Unreachable`). `ferritor_client::Server`'s `Debug` never shows its TLS configuration, which holds the client's private key. `ferritor audit verify` is offline and never resolves server settings.

### Agent

- `main` marks the process undumpable first of all, before the config or any key is read, like the server: the application next to it may run as the same user.
- Values go into the output files and nowhere else: never a log line, the status file, an error message or stdout. Logs carry paths, versions and refusals. The agent's own copies are `Zeroizing`.
- The output directory is trusted to no one but the agent: `..data`'s target is believed only if it's one of the agent's generations inside it (`files::is_generation`: one path component, starting with `..`, none of its other names, a real directory, not a symlink), and `remove_generation` removes nothing else, so a link planted to `/some/dir` or `../x` is never deleted through (`a_data_link_pointing_outside_is_never_deleted`). Each guard alone stops it; keep both. A write that fails before `..data` points at its generation (filling it, making the link, renaming it into place) removes the generation and the temporary link (`a_failed_write_leaves_nothing_behind`, `a_failed_swap_leaves_nothing_behind`).
- The output directory: a write creates a whole new generation (every file written, synced, its mode and group set) before `..data` is swapped onto it in one rename; visible names are added after the swap, and removed only for links through `..data` (never a file the agent didn't write). The previous generation stays until the next swap (`the_previous_generation_is_kept_until_the_next_swap`). Names starting with `..` are the agent's: refused as file names. The status file is written outside the set. A directory not in memory is refused unless `allow_disk`. No mode gives others any permission.
- Two kinds of refusal, sorted in one place (`agent::classify`): authoritative (`PERMISSION_DENIED`, `NOT_FOUND`, `NO_NAMESPACE`, `INVALID_ARGUMENT`, a path missing from its listing: someone decided), everything else transient (a new code is transient unless it means someone decided). Transient: the round stops, the files stay, the next try after 1 s doubling to the interval, never before the server's retry time. Authoritative: that secret alone backs off, the full interval from the first refusal (the first render too), doubling to ten intervals, never back to a second, because replicas share their identity's denial budget (`replicas_sharing_an_identity_never_drain_its_denial_budget` and `a_denied_secret_fails_once_and_backs_off_long` fail if it's shortened); its file follows `on_revoked`.
- `run` keeps a watch stream on `Agent::watch_paths` (unpinned, unrefused secrets), opened after a round, so a secret just refused is left out rather than refusing the whole stream; `ready` and `resync` run a round, `changed` calls `Agent::changed`, which reads only a secret that's due (never one backing off) and whose files don't already hold that version. The rounds go on whatever the stream does: `Agent::round_interval` stretches them only while `run` says a ready stream covers every watched path (`set_watched`, at `ready`; unset when it ends, fails or is reopened for other paths, which also brings the next round within an interval), to `WATCHED_STRETCH` intervals, at most `WATCHED_ROUNDS_MAX` (so an exchanged certificate is still renewed in time) and never below the interval; refusal backoffs and transient retries keep their own times (`rounds_stretch_while_watched`). A stream that can't open or ends is retried after 1 s doubling to the interval (`run_hears_of_a_change_at_once`).
- `Agent::poll(now)` decides everything (what's due, what's backed off) against the `now` it's given, never the clock, so the tests can simulate time; only the loop in `run` reads the clock.
- The first set is written only once every required secret has a value; the application is told of a change after every write but the first. A set is rewritten only when a file's content changes (a new version or value, a removed one coming back), never because a refusal ended (`a_refusal_ending_is_no_change`): a rewrite tells the application.
- The client certificate's files are watched (`connection`): changed on disk, the next round connects with the new pair, since the server checks the certificate on every request. With `token_file`, the certificate is exchanged two thirds into its life and after every failed round (`Connection::reset` sets `renew_now`, which skips the retry wait: a revoked CA or a cutoff must not leave the agent on a refused certificate until it's due); a failed exchange keeps a still-valid certificate.

### CSI provider

- Each pod reads as the identity its own token exchanged to, never one of the provider's: an identity is learned only from an exchange of that pod's token (remembered by the token's SHA-256 until it expires), and everything shared (reads, listings, refusals, certificates) is keyed by identity, so a pod is never served another identity's values (`reads_are_shared_within_an_identity_only`).
- Authoritative refusals are remembered per identity and path (a listing's: its prefix), and per token for a refused exchange, with the agent's backoff (from `refusal_backoff`, doubling to ten times it), and answered from memory meanwhile: the kubelet's quick retries and a rollout's pods must not drain the identity's denial budget (`retries_of_a_denied_path_reach_the_server_once_per_step`). Transient failures are `FAILED_PRECONDITION`, never `UNAVAILABLE` (`impl From<Failed> for Status`): the driver retries `UNAVAILABLE` within the call, which lets a failing first mount be masked as a remount and the pod start with an empty volume (seen in a cluster); with it, the pod waits, and a refresh leaves the volume as it is. Refusals are sorted by the agent's `classify`.
- With `watch`, one stream per identity (`keep_watching`) on its volumes' paths and prefixes, opened or widened only after a mount's reads, leaving out what they found refused: the server refuses a stream whole, so naming one item too many costs a denial and ends the identity's stream (`a_denied_volume_leaves_the_identitys_watch_alone`, and e2e's "asked once" check); one that ended isn't opened again within `refusal_backoff`. A cached read or listing past `share_reads` is used only if it carries the generation of a stream that is ready, not ended and covers it, and it carries one only if that stream was ready and covering when the call began and heard nothing during it (`watch_mark`, `still_marked`, the `heard` count): a read racing a change is never vouched for. A change drops its path's read and every listing covering it; a `resync` drops all of the identity's (`a_watch_drops_the_read_a_change_makes_stale`, `a_watch_lets_refreshes_skip_the_server_until_something_changes`).
- Every response holds the whole set (the driver writes what it's given) and never an empty one (the driver writes nothing for no files, and errors without object versions): a volume all refused is an error.
- Below a `prefix`, a secret the volume can't hold (a name starting with `..`, a file that would also be a directory) is skipped with a warning, never the volume's failure (`without_conflicts`, `a_bad_name_below_a_prefix_skips_that_secret_only`): one put by a writer under the prefix mustn't stop every pod mounting it. Of a file/directory pair the one the volume already delivered stays. An `objects` list's mistakes are its author's, and refused.
- `e2e/cluster.sh` (CI's `cluster` job) holds what only the real driver and kubelet show: a first mount refused or sealed keeps the pod waiting (never `Running` with an empty volume), a refresh while sealed leaves the volume, a new version arrives. A change to `csi` that could alter what the driver sees must keep it passing.
- Never log or return a token; values only in `File.contents`. The process is undumpable first of all, and its socket `0600`, created under a `077` umask.

## SQL and sqlx

- Each store crate checks its `query!` macros against its own database (`sqlx.toml` names the URL variable: `KEYS_DATABASE_URL`, `DATA_DATABASE_URL`). Never put a query for one database in the other's crate. Not `#[sqlx::test]` (it only reads `DATABASE_URL`).
- After changing a `query!` or a migration, run `cargo sqlx prepare` inside that crate and commit `.sqlx/` with the change. Create migrations with `sqlx migrate add` inside the crate.
- Queries over live versions keep `deleted_at IS NULL` as a plain condition next to the `path_id`, so they use the partial index `secret_versions_live` (live rows only): a path's deleted versions stay until purged and outnumber its live ones, and a query that can't use it reads every one of them (`docs/src/content/docs/operations/performance.md`, "Deleted versions").
- Prefix listing: the range from `SecretPath::descendant_range` (`path >= $1 AND path < $2`) on `paths.path`, with `current_version IS NOT NULL` so it walks `paths_live` (paths with nothing live, which stay in `paths` until their namespace is deleted, aren't in it), and the version's row by a lateral primary-key probe with `deleted_at IS NULL` and a `LIMIT 1` (so the planner can't flatten it into a hash join over every version). Only correct because `paths.path` is `COLLATE "C"`; never `LIKE` with user input (`_` is a wildcard and a legal path character), not `starts_with` (generic plans can't use the index).
- The label filter on listings is a condition on the same `paths` row (`p.labels @> $n`), in queries of their own, so a listing without a filter is exactly what it was.
- Don't make an indexed condition optional with `$n IS NULL OR …`: a reused generic plan turns it into a sequential scan. Write separate `query!` calls (see `Datastore::list`). An optional condition on top of an indexed one is fine.
- Pagination is keyset (`path > $last` with a `LIMIT`, inside the prefix's bounds, so a token can never widen a listing). The rewrap paging query forces a custom plan for its transaction (`plan_cache_mode`).
- Postgres has no unsigned integers: `INTEGER` with `CHECK`s in the schema, `u32`/`u8` in the store APIs, converted with `try_from`, never `as`.
- Store and server tests are integration tests against the real databases via `TestDatabase` (one throwaway database per test). Test helpers return `TestResult`.

## Commits and changelogs

- Commit subjects start with a conventional prefix the changelog groups by (`release-plz.toml`'s `commit_parsers`): `feat`, `fix`, `perf`, `security`, `changed`, `deprecated`, `removed`, followed by `:`, a `(scope)` or `!` (e.g. `feat: watch streams for the agent`, `fix(agent): …`, `feat!: …`); anything else, "fixture…" included, is listed under Other. `fix` and `feat` also choose the next version, `!` marks a breaking change.
- Only the merge of a release pull request is released, once `CI` passes on it (`release_always = false`, `release-plz.yml`); a fix for a failed one goes on a branch starting with `release-plz-`. The release pull request is opened or updated only when `release-pr` is started by hand (`workflow_dispatch`, on `main`), never at a push, and it refuses while a merged one isn't tagged yet.
- The workspace root is a package, `ferritor` (`src/lib.rs`, no code), only so release-plz counts commits to the files outside `crates/` (it counts a package's own files): the server's changelog, the product's, includes it. Don't give it code, dependents, a changelog or the `v*` tags (those are the server's).
- Releases are created as drafts (`git_release_draft`), because published ones are immutable: `release-assets` attaches the archives (the Dockerfile's `binaries`, the images' own build), `SHA256SUMS` and a cosign bundle per file, appends the images' digests to the notes, then publishes. Nothing may need adding to a release after that.
- Both release-plz jobs run as the `ferritor-release` GitHub App, each minting its token in the job from the `release-plz` environment's key, which only `main` may use: `release-pr` so the release pull request's checks run (`GITHUB_TOKEN` can't start them), `release` because the tag ruleset lets only the App create `v*` and `ferritor-*-v*` tags (`GITHUB_TOKEN` can't bypass a ruleset). Each asks for the permissions it needs, no more. The image jobs keep `GITHUB_TOKEN`, for ghcr.io only; cosign's signing identity is the workflow's, whichever token tags.
- The `CHANGELOG.md` files are release-plz's: it writes each release's section in the release pull request, where it may be edited before merging. Don't edit a released section afterwards, and don't add one by hand. The root one is the server's (the product's, with every released crate's commits); each other released crate has its own beside its `Cargo.toml`.

## Coding conventions

Rust style follows Apollo GraphQL's Rust best-practices handbook (<https://github.com/apollographql/rust-best-practices>): read it there, or load it however your tool loads guides (a skill, say); the repository doesn't carry a copy. Where any style guide disagrees, the workspace lints win: they deny `unwrap_used`, `expect_used` and `allow_attributes`, and forbid `unsafe_code` (each crate opts in with `[lints] workspace = true`; generated proto code is exempted with `#[expect(clippy::allow_attributes)]`). For example, a guide may allow `expect()` for invariants, but `expect_used` is denied here, so return an error instead. Property tests use `proptest`. Share count and threshold always travel together as `ferritor_core::crypto::ShareParams` (validated `2 <= threshold <= shares`), never as two loose `u8`s; its constructor takes shares first. Errors: `thiserror` in `ferritor-core` and for server error types that map to HTTP/gRPC status codes, and `anyhow` only at binary top level. A variant with a `#[from]`/`#[source]` error must not also interpolate it in its `#[error]` message (`#[error("keys database error")]`, not `"...: {0}"`), or chain printers like anyhow's `{:#}` show it twice. Interpolate only errors that can't be a source (e.g. `vsss_rs::Error`, which doesn't implement `std::error::Error`).
